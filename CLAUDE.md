# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`nattes` is a Rust library: a typesafe, in-process message queue inspired by NATS. Subjects are declared as a tree of types with the `topics!` macro, so wrong paths, parameters, or message types fail at compile time. `README.md` is the user-facing spec. Keep it in sync when public behavior changes. It is a workspace of two crates: `nattes` at the root and its proc macro crate `nattes-macros` in `macros/`, used only through `nattes::topics!`.

## Commands

The dev shell is the default `devShell` of `flake.nix` (Rust toolchain, Valgrind, gnuplot, mdBook). Enter it with `nix develop`, or let direnv load it (`.envrc`, `use flake`).

```sh
cargo build
cargo test                       # unit tests (src/tests.rs) + doctests in lib.rs
cargo test -p nattes-macros      # parser tests of the proc macro (macros/src/parse.rs)
cargo test <name>                # single test by name substring
cargo test --doc                 # doctests only (includes compile_fail checks)
cargo test --features tracing     # also the tracing test (tests/tracing.rs)
cargo clippy --workspace --all-features  # lint, as run in CI
cargo bench --bench throughput   # criterion multi-threaded throughput (noisy, wall-clock)
cargo bench --bench throughput -- fan_out   # one bench group
cargo bench --bench instructions # exact instruction counts under Valgrind (gungraun), diffed against the last run
mdbook build doc                 # the docs book (doc/), into doc/book/
mdbook serve doc                 # the same, served with live reload
```

Use `instructions` to iterate on performance: counts are reproducible, so a small change shows up. It needs Valgrind and `gungraun-runner` at the same version as the `gungraun` dev-dependency. The dev shell provides both: `flake.nix` builds the runner from crates.io, so bump its `version` and hashes there along with the dev-dependency. To compare against a fixed point, run `cargo bench --bench instructions -- --save-baseline=<name>` before a change and `-- --baseline=<name>` after it. Exception: `subscribe`/`unsubscribe` with 1000+ existing subscriptions move by up to ~8% between identical builds (likely the random hash seed of the parameter map), so treat changes there as noise unless they persist.

Both benches share the tree, `Message`, and `start()` from `benches/common/mod.rs` (a plain module, not a bench target). Put shared setup there rather than copying it.

CI (`.github/workflows/`) runs `cargo check`, `cargo build`, `cargo test --workspace`, and clippy (SARIF upload, non-blocking).

The repo is also a jujutsu repo (`.jj/`), so git may show a detached `HEAD`.

## Architecture

`src/lib.rs` holds the crate docs (including the `compile_fail` doctests) and re-exports the public API from private modules. Request/reply (and `BusError`) lives in `src/request.rs`, and tests are in `src/tests.rs`. Modules:

- **`tree.rs`, the tree (`Level`, `Step`, `subject`)**: each `Topic` enum generated by `topics!` implements `Level`, which walks one level down. `subject()` follows that chain to build `git.push` / `user.<id>.delete` strings.
- **`nav.rs`, navigation (`Prism`, `Param`, `Wild`/`Is`, `AppendParams`)**: a `Prism<A>` trait is one step down the tree, to `Prism::B` with wildcard params `Prism::Q`. `project` borrows a `B` (plus `Q`) out of an `A`, and `inject` builds an `A` from a `B` (`None` on a wildcard step). The implementations are plain values, `Plain` and `ParamStep` (fn pointers plus the `Wild`/`Is` selector), not closures, so navigating doesn't allocate. `key()` builds the step's `Key` (segment name plus `KeyParam::None`/`Wild`/`Is(ParamKey)`) only when subscribing. `ParamKey` wraps an `Arc<dyn ParamValue>` (`tree.rs`), which is any `Clone + Eq + Hash + Display` type compared and hashed through `dyn` methods. It implements `Borrow<dyn ParamValue>`, so publishing looks up the event's own `&dyn ParamValue`. `Display` only serves `subject()`. `AppendParams` concatenates wildcard param tuples, implemented up to 6 params via `impl_append!`.
- **`bus.rs`, the untyped bus (`Bus`, `Interest`, `Buffer`, `Sub`, `RoundRobin`)**: works only with `Event = Arc<dyn Level>` and `&dyn Any` matchers. Subscriptions (`Sub`) live in `Interest`, the interest trie, NATS-sublist-style and keyed by the channel's `Key` path. A subscription sits on its channel's trie node and wants everything at or below it. Each trie node lists `(segment name, Edges)` pairs (a `Vec`: siblings are few, so a scan beats hashing). `Edges { plain, wild, fixed }` holds the plain, wildcard and fixed-value children, the latter in an `imbl::HashMap<ParamKey, _>`: a persistent HAMT, so copy-on-write copies one path instead of every sibling and (un)subscribing stays O(log n) with many parameter values (measured 449k → 12k instructions at 10k subscriptions, for ~5% on parameterized publish). The trie sits in an `ArcSwap<Interest>`, so publishing reads it without a lock. (Un)subscribe updates it copy-on-write (`Arc::make_mut`) under the `state` mutex, and empty trie nodes are pruned. `publish` walks the event's `Level::step` chain without allocating: `Step::param` is a `&dyn ParamValue`, looked up by value and never formatted. It follows both the `wild` and the `Is(value)` children on parameters and runs matchers as it goes, catching panics (a panic counts as no match). The trie matches names and parameter values exactly, so only subscriptions with filters get a matcher. Queue group members are stored on their trie node as `Members`, in subscription (id) order, sharing the group's `RoundRobin` position. Groups are keyed by value (`GroupKey`, see `group.rs`) and global per bus, so one group can span several trie nodes of its topic (e.g. `user.id(alice)` and `user.id(*)`). `State.groups`, keyed by `(GroupKey, responder)` so that responders and subscribers joining the same group form two groups and `Members` stay homogeneous, counts members and forgets a group with its last one. Only in that case does `try_deliver` merge and sort the members per publish. Responders sit in their own lists on each trie node (`responders`, `responder_groups`, whose `Members` have `responder` set), and `try_deliver` takes a `const REQUEST: bool`: `deliver` (`publish`) never looks at them, so it compiles to the same loops as before responders existed (`accepts`, `try_push`, `is_idle` and `edges` are `#[inline]` because LLVM stopped inlining them otherwise, up to 20% on fan-out). `deliver_request` gives subscribers the shared event (uncounted) and each responder an event built by its `ForResponder` closure, with its own reply token (counted, even when a full buffer drops it, so the requester sees `NoReply` rather than `NoResponders`). `deliver` pushes to every non-full buffer first and only then awaits `Overflow::Wait` buffers, in a separate `deliver_waiting` future that the common no-wait path never builds. Queue groups pick one member per group (`pick`), from the round robin position: the first idle (`parked`, waiting in `next()`) accepting member, else the first busy one with room, else the first accepting one, whose overflow policy applies. Busy members are tried with `try_push::<false>`, which hands the event back when full instead of applying the policy, so checking for room and delivering take one lock. `OVERFLOW` is a const generic: as a runtime `bool` it cost ~2% on fan-out. `Buffer` is a `Mutex<VecDeque>`: a lock-free queue was measured and lost on fan-out, where each buffer has one publisher and the lock is uncontended. The `concurrent_*` stress tests cover the handoffs across threads. A push only wakes the subscriber if it is `parked`. `Overflow::Wait` publishers set `wanted` and are woken together once the buffer drains to half. `lock()` ignores poisoning on purpose.
- **`channel.rs`, `Channel<T, P, S>`**: a typed view rooted at `T`. It holds the shared `Arc<Bus>` and an `Arc<dyn Route<T, P>>`, a chain of `Hop { parent, step }` ending at `Root<R>`. A route projects a root event to `(P, &T)`, injects a `T` into a root event, and lists the `Key` path (built only on subscribe). `Channel::step` adds one `Hop`, which is one allocation per step. That keeps `at!(bus, user.id(x).delete).publish(..)` cheap; the `routing` bench builds a channel per message. `publish` exists only on `Channel<T, ()>`, so wildcard channels can't publish, and requires `S: Publish<T>`, so request leaves can't either: `impl<T> Publish<T> for T` covers levels and leaves without groups, `topics!` implements it on the group enum of a leaf with groups, and request scopes don't get it. This is checked at compile time and relied on by `compile_fail` doctests.
- **`subscription.rs`, subscriptions**: `SubscriptionBuilder` implements `IntoFuture` (ready immediately). `SubscriptionBuilder<T, P, S, K>` has a mode `K`: `Subscribe` starts a `Subscription`, `Respond` (from `Channel::respond`, only where `S: Answer<T>`) a `Responder`, a `Stream` of `Incoming`. Both wrap `Active`, the registration and buffer, and dropping it unsubscribes and closes the buffer, which clears pending requests so requesters get `NoReply`. `Msg<T, P>` keeps the root event and re-projects on `Deref`/`params()`.
- **`group.rs`, queue groups (`QueueGroup`, `InScope`, `GroupKey`)**: `git [A, B(T)] { … }`, `leaf [ … ]: Msg` or `root [ … ] { … }` (right after the name and parameter, chains too; inner attributes `#![…]` go on the enum), generates an enum (named `Queue` for a level, `LeafQueue` for a leaf, like `Topic`) deriving `Clone + Eq + Hash` that implements `QueueGroup` and `InScope<S>` for exactly one scope `S`: the level's `Topic`, or for a leaf the group enum itself (the message type may appear at several leaves). `Channel<T, P, S = T>` carries `S` as a phantom; a leaf with groups gets it via `with_scope()`. `SubscriptionBuilder::queue` requires `G: QueueGroup + InScope<S>`, so a group is joined only on its declaring topic. `GroupKey` is an `Arc<dyn GroupValue>` hashed with the `TypeId`, so equal variant names in different enums are different groups.
- **`macros.rs`**: `at!` turns `a.b(x).c()` into calls on generated `Steps` types (`()`/`_` becomes `Wild`, a value becomes `Is(v)`): `@go` takes one segment, `@next` what follows it. An incomplete path (`git.`, or none) goes on with the placeholder name `expected_a_topic_name`, which is what lets rust-analyzer complete there: it completes in a macro only if the real input expands too, with the same tokens at each level of expansion as its copy with a fake name at the cursor. So don't turn those cases into `compile_error!`. `topics!` only forwards to the proc macro `__topics!` with `$crate` as the first token.
- **`macros/`, the `topics!` proc macro (`nattes-macros`)**: `parse.rs` reads the tree into `Entry`s (`Kind::Level`, also for a chain `a.b`, `Leaf { msg, reply }` with `reply` set by `=> Reply`, `Mount`; the root is an `Entry` too) and collects errors entry by entry: a wrong entry is skipped up to the next `,` outside `<…>` and its siblings still expand, so editors keep resolving the tree while it's typed. Only doc attributes go on entries; docs on a chain go to its last topic; each `[ … ]` becomes a `GroupEnum`; the root is written like any level (`topics! { name { … } }`, always a `pub` module), and doc attributes before its name go on the root module, the others on every `Topic`. `expand.rs` generates one module per level with `use super::*`, which is why `topics!` must be used at module level. Variants are the names in camel case (`camel()`) and, like the `PushQueue` enums and the methods, carry the span of the name, so go to definition lands in `topics!`; `Topic`, `Steps` and `Queue` carry the level's name. Raw identifiers are unrawed for subjects and variants. A request leaf `name: Msg => Reply` holds its `Msg` like any leaf, with the same step; its scope is its `NameQueue`, or an empty `NameScope` enum (not `NameRequest`, a common message name that the generated item would shadow), with `impl Answer<Msg> { type Reply }`; the group enum of any other leaf gets `impl Publish<Msg>`. Variants and `Steps` methods get a doc stating their subject (`user.id.*.delete`), after the user's docs.

`request.rs` holds request/reply. A request leaf's variant holds its message, so subscribers (on the leaf or a level above) see the plain payload. `request`/`scatter` (on `Channel<M, (), S>` where `S: Answer<M>`) build the event as `publish` would and give it to subscribers; each responder gets an `Answering<R> { event, reply }`, one allocation holding the shared event and a clone of the token (it implements `Level` only to sit in a buffer, delegating `step`). They then drop their own token so only responders hold one. `Incoming::new` unwraps the `Answering` (`Arc<dyn Level>` upcast to `Arc<dyn Any>`, downcast, `Arc::into_inner`: a responder's event has one holder). This replaced a hidden `Request<M, R>` stored in the variant, built through an erased `inject_request` on every step: level subscribers saw the hidden type, and `scatter` cost 21–33% more instructions. `Reply::One` is an `Arc<Mutex<Option<oneshot::Sender>>>` (first reply wins; the requester sees `NoReply` once every token is gone), `Reply::Many` an unbounded mpsc sender cloned per responder (`scatter`: `Replies` ends after as many replies as responders reached, or once every token is gone). `Incoming` (not `Clone`) takes the token in `respond(self, reply)` and sends after releasing the lock. The only tokio runtime dependency is the timer in `request_timeout`; everything else must stay executor-agnostic (tokio is used only for `sync`).

## Conventions

- Compile-time guarantees are part of the API. When changing navigation or publishing, update the `compile_fail` doctests in `lib.rs` and the "Compile-time checks" section of the README.
- Every handle and future must stay `Send + Sync`, and messages are `Send + Sync + 'static`.
- Generated code follows Rust naming conventions: names are snake case (modules, methods, subject segments) and become camel case `Topic` variants. Only clippy lints about method names (`clippy::new_ret_no_self`, …) are silenced, since `Steps` methods are topic names.
- Logging goes through the `trace!`/`debug!`/`warning!` macros in `src/log.rs`, which compile to nothing without the `tracing` feature. Never log while holding a lock: a tracing subscriber is user code. Format subjects and patterns lazily (`subject = %Subject(..)`, `pattern = %Pattern(..)`), never with `subject()`. The test is its own binary (`tests/tracing.rs`) because tracing caches callsite interest globally, so it races with tests on other threads.
- Use the terms of `doc/src/vocabulary.md` in code, docs and comments; don't introduce synonyms. Update it when a concept is added or renamed.
- `TODO.md` tracks planned features.
