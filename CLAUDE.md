# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`nattes` is a Rust library: a typesafe, in-process message queue inspired by NATS. Subjects are declared as a tree of types with the `events!` macro, so wrong paths, parameters, or message types fail at compile time. `README.md` is the user-facing spec. Keep it in sync when public behavior changes. It is a workspace of two crates: `nattes` at the root and its proc macro crate `nattes-macros` in `macros/`, used only through `nattes::events!`.

## Commands

The dev shell is the default `devShell` of `flake.nix` (Rust toolchain, Valgrind, gnuplot). Enter it with `nix develop`, or let direnv load it (`.envrc`, `use flake`).

```sh
cargo build
cargo test                       # unit tests (src/tests.rs) + doctests in lib.rs
cargo test -p nattes-macros      # parser tests of the proc macro (macros/src/parse.rs)
cargo test <name>                # single test by name substring
cargo test --doc                 # doctests only (includes compile_fail checks)
cargo test --features tracing     # also the tracing test (tests/tracing.rs)
cargo clippy --workspace --all-features  # lint, as run in CI
cargo bench --bench throughput   # criterion multi-threaded throughput (noisy, wall-clock)
cargo bench --bench throughput -- fan_out   # one bench group
cargo bench --bench instructions # exact instruction counts under Valgrind (gungraun), diffed against the last run
```

Use `instructions` to iterate on performance: counts are reproducible, so a small change shows up. It needs Valgrind and `gungraun-runner` at the same version as the `gungraun` dev-dependency. The dev shell provides both: `flake.nix` builds the runner from crates.io, so bump its `version` and hashes there along with the dev-dependency. To compare against a fixed point, run `cargo bench --bench instructions -- --save-baseline=<name>` before a change and `-- --baseline=<name>` after it. Exception: `subscribe`/`unsubscribe` with 1000+ existing subscriptions move by up to ~8% between identical builds (likely the random hash seed of the parameter map), so treat changes there as noise unless they persist.

Both benches share the event tree, `Payload`, and `start()` from `benches/common/mod.rs` (a plain module, not a bench target). Put shared setup there rather than copying it.

CI (`.github/workflows/`) runs `cargo check`, `cargo build`, `cargo test --workspace`, and clippy (SARIF upload, non-blocking).

The repo is also a jujutsu repo (`.jj/`), so git may show a detached `HEAD`.

## Architecture

`src/lib.rs` holds the crate docs (including the `compile_fail` doctests) and re-exports the public API from private modules. Request/reply (and `BusError`) lives in `src/request.rs`, and tests are in `src/tests.rs`. Modules:

- **`tree.rs`, event tree (`Node`, `Step`, `subject`)**: each `Topic` enum generated by `events!` implements `Node`, which walks one level down. `subject()` follows that chain to build `git.push` / `user.<id>.delete` strings.
- **`nav.rs`, navigation (`Prism`, `Param`, `Wild`/`Is`, `AppendParams`)**: a `Prism<A>` trait is one step down the tree, to `Prism::B` with wildcard params `Prism::Q`. `project` borrows a `B` (plus `Q`) out of an `A`, and `inject` builds an `A` from a `B` (`None` on a wildcard step). The implementations are plain values, `Plain` and `ParamStep` (fn pointers plus the `Wild`/`Is` selector), not closures, so navigating doesn't allocate. `key()` builds the step's `Key` (segment name plus `None`/`Any`/`Is(ParamKey)`) only when subscribing. `ParamKey` wraps an `Arc<dyn ParamValue>` (`tree.rs`), which is any `Clone + Eq + Hash + Display` type compared and hashed through `dyn` methods. It implements `Borrow<dyn ParamValue>`, so publishing looks up the event's own `&dyn ParamValue`. `Display` only serves `subject()`. `AppendParams` concatenates wildcard param tuples, implemented up to 6 params via `impl_append!`.
- **`bus.rs`, untyped bus core (`Core`, `Interest`, `Queue`, `Entry`, `Group`)**: works only with `Event = Arc<dyn Node>` and `&dyn Any` matchers. Subscriptions live in `Interest`, a NATS-sublist-style trie keyed by the channel's `Key` path. A subscription sits on its channel's node and wants everything at or below it. Each node lists `(segment name, Edges)` pairs (a `Vec`: siblings are few, so a scan beats hashing). `Edges` holds the plain, `Any`, and fixed-value children, the latter in an `imbl::HashMap<ParamKey, _>`: a persistent HAMT, so copy-on-write copies one path instead of every sibling and (un)subscribing stays O(log n) with many parameter values (measured 449k → 12k instructions at 10k subscriptions, for ~5% on parameterized publish). The trie sits in an `ArcSwap<Interest>`, so publishing reads it without a lock. (Un)subscribe updates it copy-on-write (`Arc::make_mut`) under the `state` mutex, and empty nodes are pruned. `publish` walks the event's `Node::step` chain without allocating: `Step::param` is a `&dyn ParamValue`, looked up by value and never formatted. It follows both `Any` and `Is(value)` edges on parameters and runs matchers as it goes, catching panics (a panic counts as no match). The trie matches names and parameter values exactly, so only subscriptions with filters get a matcher. Queue group members are stored on their node as `Members`, in subscription (id) order. Groups are keyed by value (`GroupKey`, see `group.rs`) and global per bus, so one group can span several nodes of its topic (e.g. `user.id(alice)` and `user.id(*)`). `State.groups` counts members and forgets a group with its last one. Only in that case does `route` merge and sort the members per publish. `deliver` pushes to every non-full queue first and only then awaits `Overflow::Wait` queues, in a separate `wait` future that the common no-wait path never builds. Queue groups pick one member per group (`pick`): the first idle (`parked`, waiting in `next()`) accepting member from the round robin position, else the first accepting one. `Queue` is a `Mutex<VecDeque>`: a lock-free queue was measured and lost on fan-out, where each queue has one publisher and the lock is uncontended. The `concurrent_*` stress tests cover the handoffs across threads. A push only wakes the subscriber if it is `parked`. `Overflow::Wait` publishers set `wanted` and are woken together once the queue drains to half. `lock()` ignores poisoning on purpose.
- **`channel.rs`, `Channel<T, P>`**: a typed view rooted at `T`. It holds the shared `Arc<Core>` and an `Arc<dyn Route<T, P>>`, a chain of `Hop { parent, step }` ending at `Root<R>`. A route projects a root event to `(P, &T)`, injects a `T` into a root event, and lists the `Key` path (built only on subscribe). `at_prism` adds one `Hop`, which is one allocation per step. That keeps `topic!(bus, user.id(x).delete).publish(..)` cheap; the `routing` bench builds a channel per message. `publish` exists only on `Channel<T, ()>`, so wildcard channels can't publish. This is checked at compile time and relied on by `compile_fail` doctests.
- **`subscription.rs`, subscriptions**: `SubscriptionBuilder` implements `IntoFuture` (ready immediately). `Subscription` is a `Stream`, and dropping it unsubscribes and closes the queue, which clears pending requests so requesters get `NoReply`. `Msg<T, P>` keeps the root event and re-projects on `Deref`/`params()`.
- **`group.rs`, queue groups (`QueueGroup`, `InScope`, `GroupKey`)**: `git [A, B(T)] { … }`, `leaf [ … ]: Msg` or `root [ … ] { … }` (right after the name and parameter, chains too; inner attributes `#![…]` go on the enum), generates an enum (named `Queue` for a level, `LeafQueue` for a leaf, like `Topic`) deriving `Clone + Eq + Hash` that implements `QueueGroup` and `InScope<S>` for exactly one topic `S`: the level's `Topic`, or for a leaf the group enum itself (the message type may appear at several leaves). `Channel<T, P, S = T>` carries `S` as a phantom; a leaf with groups gets it via `on_topic()`. `SubscriptionBuilder::queue` requires `G: QueueGroup + InScope<S>`, so a group is joined only on its declaring topic. `GroupKey` is an `Arc<dyn GroupValue>` hashed with the `TypeId`, so equal variant names in different enums are different groups.
- **`macros.rs`**: `channel!` makes `Channel::<mod::Topic>::new()`. `topic!` turns `a.b(x).c()` into calls on generated `Steps` types (`()`/`_` becomes `Wild`, a value becomes `Is(v)`): `@go` takes one segment, `@next` what follows it. An incomplete path (`git.`, or none) goes on with the placeholder name `expected_a_topic_name`, which is what lets rust-analyzer complete there: it completes in a macro only if the real input expands too, with the same tokens at each level of expansion as its copy with a fake name at the cursor. So don't turn those cases into `compile_error!`. `events!` only forwards to the proc macro `__events!` with `$crate` as the first token.
- **`macros/`, the `events!` proc macro (`nattes-macros`)**: `parse.rs` reads the tree into `Entry`s (`Kind::Tree`, also for a chain `a.b`, `Leaf`, `Mount`; the root is an `Entry` too) and collects errors entry by entry: a wrong entry is skipped up to the next `,` outside `<…>` and its siblings still expand, so editors keep resolving the tree while it's typed. Only doc attributes go on entries; docs on a chain go to its last topic; the root is written like a subtree (`events! { name { … } }`, always a `pub` module), and doc attributes before its name go on the root module, the others on every `Topic`. `expand.rs` generates one module per level with `use super::*`, which is why `events!` must be used at module level. Variants are the names in camel case (`camel()`) and, like the `PushQueue` enums and the methods, carry the span of the name, so go to definition lands in `events!`; `Topic`, `Steps` and `Queue` carry the level's name. Raw identifiers are unrawed for subjects and variants. Variants and `Steps` methods get a doc stating their subject (`user.id.*.delete`), after the user's docs.

`request.rs` adds `Request<RQ, RP>` as a leaf message type wrapping either a tokio oneshot (`request` / `request_timeout`, first reply wins) or an unbounded mpsc (`scatter` / `gather`, one reply per responder). `scatter` expects as many replies as `deliver` reached, so `Replies` ends after that many or once every holder dropped the request. The only tokio runtime dependency is the timer in `request_timeout` and `gather`; everything else must stay executor-agnostic (tokio is used only for `sync`).

## Conventions

- Compile-time guarantees are part of the API. When changing navigation or publishing, update the `compile_fail` doctests in `lib.rs` and the "Compile-time checks" section of the README.
- Every handle and future must stay `Send + Sync`, and messages are `Send + Sync + 'static`.
- Generated code follows Rust naming conventions: names are snake case (modules, methods, subject segments) and become camel case `Topic` variants. Only clippy lints about method names (`clippy::new_ret_no_self`, …) are silenced, since `Steps` methods are topic names.
- Logging goes through the `trace!`/`debug!`/`warning!` macros in `src/log.rs`, which compile to nothing without the `tracing` feature. Never log while holding a lock: a tracing subscriber is user code. Format subjects lazily (`%Subject(..)`, `%Pattern(..)`), never with `subject()`. The test is its own binary (`tests/tracing.rs`) because tracing caches callsite interest globally, so it races with tests on other threads.
