# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`nattes` is a Rust library: a typesafe, in-process message queue inspired by NATS. Subjects are declared as a tree of types with the `topics!` macro, so wrong paths, parameters, or message types fail at compile time. `README.md` is the user-facing spec. Keep it in sync when public behavior changes. It is a workspace of two crates: `nattes` at the root and its proc macro crate `nattes-macros` in `macros/`, used only through `nattes::topics!`.

## Commands

The dev shell is the default `devShell` of `flake.nix` (Rust toolchain, Valgrind, gnuplot, mdBook). Enter it with `nix develop`, or let direnv load it (`.envrc`, `use flake`).

```sh
cargo build
cargo test                       # unit tests (src/tests.rs) + doctests in lib.rs
cargo test -p nattes-macros      # parser tests of the proc macro (macros/src/parse.rs)
cargo test <name>                # single test by name substring
cargo test --doc                 # doctests only (includes compile_fail checks)
cargo test --features tracing     # also the tracing test (tests/tracing.rs)
cargo test --features bridge --test bridge  # two buses over a bridge, in memory and on a Unix socket
cargo clippy --workspace --all-features  # lint, as run in CI
cargo bench --bench throughput   # criterion multi-threaded throughput (noisy, wall-clock)
cargo bench --bench throughput -- fan_out   # one bench group
cargo bench --bench instructions # exact instruction counts under Valgrind (gungraun), diffed against the last run
mdbook build doc                 # the docs book (doc/), into doc/book/
mdbook serve doc                 # the same, served with live reload
```

Use `instructions` to iterate on performance: counts are reproducible, so a small change shows up. It needs Valgrind and `gungraun-runner` at the same version as the `gungraun` dev-dependency. The dev shell provides both: `flake.nix` builds the runner from crates.io, so bump its `version` and hashes there along with the dev-dependency. To compare against a fixed point, run `cargo bench --bench instructions -- --save-baseline=<name>` before a change and `-- --baseline=<name>` after it. Exception: `subscribe`/`unsubscribe` with 1000+ existing subscriptions move by up to ~8% between identical builds (likely the random hash seed of the parameter map), so treat changes there as noise unless they persist.

Both benches share the tree, `Message`, and `start()` from `benches/common/mod.rs` (a plain module, not a bench target). Put shared setup there rather than copying it.

CI (`.github/workflows/`) runs `cargo check`, `cargo build`, `cargo test --workspace`, and clippy (SARIF upload, non-blocking).

The repo is also a jujutsu repo (`.jj/`), so git may show a detached `HEAD`.

Project skills in `.claude/skills/`: `verify` (the full check matrix, beyond what CI runs), `perf-iterate` (the baseline workflow above), `api-change` (what to update with a public or compile-time change), `nattes-review` (the conventions below as a review pass), `macro-expand` (`topics!` output with `cargo expand`). `.claude/settings.json` enables the rust-analyzer LSP and context7 plugins.

## Architecture

`src/lib.rs` holds the crate docs (including the `compile_fail` doctests) and re-exports the public API from private modules. Request/reply (and `BusError`) lives in `src/request.rs`, bridges in `src/bridge.rs` and `src/wire.rs`, and tests are in `src/tests.rs` (unit), `tests/bridge.rs` and `tests/tracing.rs`. Modules:

- **`tree.rs`, the topic traits (`Topic`, `Level`, `Leaf`, `Publish`, `Request`, `ParamValue`)**: the `T` of a channel is a `Topic`: a level's `Topic` enum or a leaf type (`git::PushLeaf`), both empty enums generated by `topics!`. `Topic::View<'a>` is what subscribers see (`&Msg` on a leaf, the level's `TopicRef<'a>` on a level), built by `view(below, payload)` from the event's segments below the channel. Levels only subscribe: publishing a level value and `try_into_inner` on a level were dropped to cut generated code (an owned `Topic` enum per level, rebuilt from the segments), so `try_into_inner` is on leaves only, through `event::take`. Leaf types exist because Rust can't otherwise tell `Channel<Msg>` from `Channel<git::Topic>` to give leaves `Deref` and levels `view()`; they also replace the old scope phantom: `Publish { type Msg }` (implemented by `topics!` on non-request leaves, its own `Msg` so that publishing on a level reports one error) gates `publish`, `Request { type Reply }` gates `request`/`scatter`/`respond`. `ParamValue` is any `Clone + Eq + Hash + Display` type, compared and hashed through `DynValue` (shared with `GroupKey`; `dyn` impls of `PartialEq`/`Hash`), and `__param` is bounded on it so that `topics!` rejects other parameter types where the tree is declared; `Display` only serves `subject()` (`Subject`, escaping with `Escaped`).
- **`nav.rs`, paths (`Node`, `Seg`, `SegInfo`, `Param`, `Wild`, `Params`, `AppendParams`, `Shape`)**: a channel holds an `Arc<Node>`: its whole path flat (`Path`, a `SmallVec<[Seg; 4]>`) and a `wild` bitmask. A `Seg` is two words, a `&'static SegInfo` (segment id and name, one `const` per topic generated by `topics!` as `&const { SegInfo::new(id, name) }`) and an optional `Arc<dyn ParamValue>`, so a step copies a few segments (refcount increments for fixed values) and allocates one node, and `keys()` reuses the value `Arc`s as `ParamKey`s. An event holds the `Arc<Node>` of the channel it was published on (bridge decoding builds a fresh node). Measured on the way here (instructions vs. v1, throughput with ad-hoc probes): an `Arc<dyn Route>` chain of `Hop`s with the root enum as event (v1); nodes linked to their parent (an event then kept the chain alive and the subscriber freed it across threads: −10–17% throughput on `routing`, virtual calls cost 7–17% on publishing); an event copying the path (+27% to publish on a reused channel, 3× on `publish_many`); a subject cached in the node (+40% to build a channel per message); a copy for the first event then a shared one (in between on both). The chosen layout: reused channels and batches beat v1, a channel built per message costs ~+20% instructions but matches or beats v1's throughput. `Param<V>` is implemented for `Wild` and for every `V: ParamValue` (no overlap: `Wild` isn't `Display`), so a fixed parameter is passed as is: `id(7)`. `P` is a tuple type computed by `AppendParams` (up to 6), and values are read back by `Params::from_values`: `Msg`, `Incoming` and filters copy the channel's `Shape` (depth and wildcard mask), not its `Arc<Node>`, whose count the publisher touches too. `ParamKey` (an `Arc<dyn ParamValue>`) implements `Borrow<dyn ParamValue>`, so publishing looks up the event's own value.
- **`event.rs`, events (`Envelope`, `Event`)**: `Event = Arc<dyn Envelope>`; `Env<M>` holds the subject (`Arc<Node>`), an `imported` flag (received from a bridge, with the `bridge` feature) and the message. `take` downcasts through `into_any` and `Arc::try_unwrap`s, giving the event back if shared.
- **`bus.rs`, the untyped bus (`Bus`, `Interest`, `Buffer`, `Sub`, `RoundRobin`)**: works only with `Event`s and matchers `Fn(&dyn Envelope, &[Seg])` (the event's segments, shared with filters: collecting them per filter once doubled the cost of filtered publishing). Subscriptions (`Sub`) live in `Interest`, the interest trie, NATS-sublist-style and keyed by the channel's `Key` path. A subscription sits on its channel's trie node and wants everything at or below it. Each trie node lists `(segment id, Edges)` pairs (a `Vec`: siblings are few, so a scan beats hashing). `Edges { plain, wild, fixed }` holds the plain, wildcard and fixed-value children, the latter in an `imbl::HashMap<ParamKey, _>`: a persistent HAMT, so copy-on-write copies one path instead of every sibling and (un)subscribing stays O(log n) with many parameter values (measured 449k → 12k instructions at 10k subscriptions, for ~5% on parameterized publish). A node's subscriptions (`subs`, `responders`, each group's members) are a `Subs`: in id order, in shared chunks of up to 64 (`Vec<Arc<Vec<Arc<Sub>>>>`), so copying a node copies one count per chunk and a change copies one chunk (254k → 7k instructions to subscribe with 10k subscriptions on one channel). Publishing loops over plain slices: `imbl::Vector` was tried and cost publishing up to 50% (building its focus, indexing it out of line). The trie sits in an `ArcSwap<Interest>`, so publishing reads it without a lock. (Un)subscribe updates it copy-on-write (`Arc::make_mut`) under the `state` mutex, and empty trie nodes are pruned. `visit` follows both the `wild` and the `Is(value)` children on parameters and runs matchers as it goes, catching panics (a panic counts as no match). The trie matches ids and parameter values exactly, so only subscriptions with filters get a matcher. Queue group members are stored on their trie node as `Members`, in subscription (id) order, sharing the group's `RoundRobin` position. Groups are keyed by value (`GroupKey`, see `group.rs`) and the segment ids of their topic's path, without parameters, so one group can span several trie nodes of its topic (e.g. `user.id(alice)` and `user.id(Wild)`), while each mount of a tree has its own groups. `State.groups`, keyed by `GroupId` = `(GroupKey, ids, responder)` so that responders and subscribers joining the same group form two groups and `Members` stay homogeneous, counts members and forgets a group with its last one. `pick_group` skips groups seen earlier in the publish and merges and sorts the members of a group spread over several trie nodes. Responders sit in their own lists on each trie node (`responders`, `responder_groups`), and `try_deliver` takes a `const REQUEST: bool`: `deliver` (`publish`) never looks at them, so it compiles to the same loops as before responders existed (`accepts`, `try_push`, `is_idle` and `edges` are `#[inline]` because LLVM stopped inlining them otherwise, up to 20% on fan-out). `deliver_request` gives subscribers the shared event (uncounted) and each responder an event built by its `ForResponder` closure, with its own reply token (counted, even when a full buffer drops it, so the requester sees `NoReply` rather than `NoResponders`). `deliver` pushes to every non-full buffer first and only then awaits `Overflow::Wait` buffers, in a separate `deliver_waiting` future that the common no-wait path never builds. `deliver_many` (`publish_many`) walks the trie once for events of one subject and gives each plain subscription its accepted events with `Buffer::push_many`, under one lock (2.3–2.5× fewer instructions than one `publish` each); queue groups still pick per event. `try_push` and `push_many` share `push_full` (the overflow policy) and `try_deliver` and `try_deliver_many` share `deliver_to_groups`, but the room-left push stays inline in each: sharing it as a helper returning `(Push, Option<Event>)` cost publish_many +40% and fan-out +8%, and calling `deliver_to_groups` without groups +2%. Queue groups pick one member per group (`pick`), from the round robin position: the first idle (`parked`, waiting in `next()`) accepting member, else the first one with room. The second pass tries every accepting member, idle or not: one that parked between the passes used to be skipped by both, losing the message (`publish` returned 0; found by the `queue_group/1` throughput bench hanging, covered by `concurrent_publishers_to_a_waiting_queue_group`). When all are full, the group waits if any of them has `Overflow::Wait` (`Picked::Wait`: `Buffer::push_wait_any` waits on all of those and pushes to the first with room, boxed so its state doesn't grow every publishing future), else the first one's overflow policy applies. Busy members are tried with `try_push::<false>`, which hands the event back when full instead of applying the policy, so checking for room and delivering take one lock. `OVERFLOW` is a const generic: as a runtime `bool` it cost ~2% on fan-out. `Buffer` is a `Mutex<VecDeque>`: a lock-free queue was measured and lost on fan-out, where each buffer has one publisher and the lock is uncontended. A handler's `Buffer` has a `HandlerFn` and stores nothing: `try_push` calls it (catching panics) while `parked`, which stays set until `close`, so queue groups see handlers as idle. `pop_many`/`poll_many` back `recv_many`. The `concurrent_*` stress tests cover the handoffs across threads. A push only wakes the subscriber if it is `parked`. Waking is what bounds buffered fan-out with fast subscribers: a subscriber faster than its publisher parks after nearly every message, and each park costs the publisher a cross-thread wake (v2's cheaper `Msg` made subscribers park ~6× more than v1's, so `fan_out` with no-op subscribers is ~25% below v1, while with ~0.2–0.6 µs of work per message it is 15–35% above). Yielding before parking was tried and dropped: with tokio a self-woken task takes the LIFO slot and starves a publisher on the same worker (−49% on `fan_in/1`). Handlers (`fan_out_handlers`) and batches (`fan_out_batched`) avoid the wakes: 2–2.4× v1's fan-out. `Overflow::Wait` publishers set `wanted` and are woken together once the buffer drains to half: they register their waker in `BufferState::waiting` (no `Notify`, no runtime), woken after unlocking, and retry only once `wakes` moved, so a spurious poll doesn't refill the buffer one slot at a time. `lock()` ignores poisoning on purpose. Watchers (`Bus::watch`, for bridges, behind the `bridge` feature) get the path of every watched subscription, then each `Change`, sent to unbounded `futures` channels under the `state` lock so they arrive in order; responders and bridge exports aren't watched.
- **`channel.rs`, `Channel<T, P>`**: a typed view rooted at `T`. It holds the shared bus as an `Arc<Handle>` (subscriptions hold the `Arc<Bus>` itself; the last `Handle` dropped closes the bus: `Bus::close` empties the trie, drops the watchers and `Buffer::end`s every buffer, which keeps its events, so streams drain then yield `None`) and its path, an `Arc<Node>`. `__plain`/`__param` (called by the generated `Steps` impls) make one `Node` each, so `bus.user().id(x).delete().publish(..)` costs one allocation per step; the `routing` bench builds a channel per message. `publish` and `publish_many` exist only on `Channel<T, ()>`, so wildcard channels can't publish, and require `T: Publish`, so request leaves can't either. `publish_many` delivers all its events at once: they share the leaf's path. This is checked at compile time and relied on by `compile_fail` doctests.
- **`subscription.rs`, subscriptions**: `SubscriptionBuilder<T, P, K>` implements `IntoFuture` (ready immediately), with a mode `K`: `Subscribe` starts a `Subscription`, `Respond` (from `Channel::respond`, only where `T: Request`) a `Responder`, a `Stream` of `Incoming`; `.handler(f)` starts a `Handler` instead. All wrap `Active`, the registration and buffer, and dropping it unsubscribes and closes the buffer, which clears pending requests so requesters get `NoReply`. Filters are typed on the way in (`filter` needs `P: Params`) into closures on the envelope and segments. `Msg<T, P>` keeps the event and the channel's path: `Deref` on leaves, `view()` on any topic, `params()` where `P: Params`.
- **`group.rs`, queue groups (`QueueGroup`, `InScope`, `GroupKey`)**: groups are declared in the tree (`git [Mailer] { … }`, `push [Indexer(u32)]: Msg`) and `topics!` generates a group enum per topic (`Queue` in a level's module, `NameQueue` next to a leaf type) implementing the marker traits `QueueGroup` (no blanket impl) and `InScope<T>` for the topic's `Topic` enum or leaf type. `queue` requires `G: QueueGroup + InScope<T>`, which is all it takes since every leaf has its own type: v1 needed a scope phantom on `Channel` because a leaf channel's `T` was its message type, shared by several leaves. Both traits have `on_unimplemented` messages, relied on by the README. `GroupKey` is an `Arc<dyn GroupValue>` hashed with the `TypeId`, so equal values of different enums are different groups; it is only built on (un)subscribe, so delivery doesn't see the types.
- **`wire.rs`, encoding for bridges (`Codec`, `Wire`)**: behind the `bridge` feature, like `bridge.rs`, the watchers in `bus.rs` and the `imported` flag. the user implements `Codec<M>` (encode into a `Vec`, decode from a slice) for every message and parameter type, usually one generic impl over serde; nattes has no serialization of its own. `topics!` implements `Wire<C>` on every `Topic` enum (bounded on its children's `Wire<C>` and `C: Codec<Param>`) and leaf type (`C: Codec<Msg>`): `encode` writes each parameter length-prefixed then the payload, `decode` rebuilds the path from segment ids (an unknown id is `WireError::UnknownTopic`) and makes an imported event. A message frame body is the relative segment ids (varint count, `u32` LE each), then that.
- **`bridge.rs`, `Bridge`**: `run(sink, stream)` joins a writer (hello, then interest changes and exported messages, flushed per batch) and a reader (checks the hello's `FRAME_VERSION`, counts the other side's patterns, decodes and delivers its messages, which waits on local `Overflow::Wait` buffers and so backpressures the transport) with `select`, ending with either. The export is one subscription on the bridged channel, not one per pattern, so a message matching several patterns is sent once; its matcher skips imported events (no forwarding between bridges: full mesh, like NATS routes) and checks `Patterns`, a trie of segment ids in an `ArcSwap` rebuilt by the reader. Interest is relative to the bridged channel (`relative`): a subscription above it covers everything, fixed parameters widen to `*`. Paths in frames are relative too, so each side can mount the tree elsewhere. Request/reply stays local.
- **`macros.rs`**: `topics!` only forwards to the proc macro `__topics!` with `$crate` as the first token. The `at!` macro is gone: steps are plain trait methods, which rust-analyzer completes without the placeholder-name trick `at!` needed.
- **`macros/`, the `topics!` proc macro (`nattes-macros`)**: `parse.rs` reads the tree into `Entry`s (`Kind::Level`, also for a chain `a.b`, `Leaf { msg, reply }` with `reply` set by `=> Reply`, `Mount`; the root is an `Entry` too; `groups`, a `GroupEnum` of inner attributes and variants, read by `group_enum` after the name and parameter, not allowed on mounts) and collects errors entry by entry: a wrong entry is skipped up to the next `,` outside `<…>` and its siblings still expand, so editors keep resolving the tree while it's typed. It rejects duplicate names, names in `RESERVED` (methods of `Channel` and of std prelude traits it implements, which would shadow or clash with a step), and siblings whose `segment_id` (FNV-1a of the name) collide. Only doc attributes go on entries; docs on a chain go to its last topic; the root is written like any level (`topics! { name { … } }`, always a `pub` module), and doc attributes before its name go on the root module, the others on every `TopicRef`. `expand.rs` generates one module per level with `use super::*`, which is why `topics!` must be used at module level: an empty `Topic`, `TopicRef` (with a hidden uninhabited variant on an empty level, to use its lifetime), `impl Topic/Level` and, with nattes-macros's `bridge` feature (enabled by nattes's), `Wire<C>` (matching on segment ids), the `Steps` trait and its impl on `Channel<Topic, P>`, a leaf type `NameLeaf` per leaf (`impl Topic/Leaf`, `Wire<C>` with bridges, and `Publish` or `Request`), group enums (`Queue` for the level, `NameQueue` next to a leaf type, deriving `Clone, PartialEq, Eq, Hash`, the user's inner attributes turned outer, `impl QueueGroup` and `InScope<Topic or NameLeaf>`), and in the root's module a `prelude` re-exporting every `Steps as _`, plus `pub use <mount>::prelude::*` per mount (relative mount paths are prefixed with `super::super::`, the module around `topics!`). `TopicRef` variants, leaf types, group enums and methods carry the span of the name, so go to definition lands in `topics!`; `Topic`, `TopicRef` and `Steps` carry the level's name. Raw identifiers are unrawed for subjects and variants. Variants and `Steps` methods get a doc stating their subject (`user.id.*.delete`), after the user's docs.

`request.rs` holds request/reply. A request leaf's event holds its message, so subscribers (on the leaf or a level above) see the plain payload. `request`/`scatter` (on `Channel<L>` where `L: Request`) build the event as `publish` would and give it to subscribers; each responder gets an `Answering<R> { event, reply }`, one allocation holding the shared event and a clone of the token (it implements `Envelope` by delegating). They then drop their own token so only responders hold one. `Incoming::new` unwraps the `Answering` (`into_any`, downcast, `Arc::into_inner`: a responder's event has one holder). This replaced a hidden `Request<M, R>` stored in the message: level subscribers saw the hidden type, and `scatter` cost 21–33% more instructions. `Reply::One` is an `Arc<Mutex<Option<oneshot::Sender>>>` (first reply wins; the requester sees `NoReply` once every token is gone), `Reply::Many` an unbounded mpsc sender cloned per responder (`scatter`: `Replies` ends after as many replies as responders reached, or once every token is gone). `Incoming` (not `Clone`) holds the token as a public `ReplyToken` (wrapping `Reply`), which `try_into_inner` hands out with the payload. `respond(self, reply)` takes the token and sends after releasing the lock. The crate depends on no async runtime (tokio and tokio-util are only dev-dependencies): reply tokens are `futures::channel` types, bridges take `futures` `Sink`/`Stream`s of `bytes::Bytes`, and timeouts are left to the caller's runtime (`tokio::time::timeout(d, chan.request(..))`, `take_until` on `Replies`).

Measured and not done: a per-channel cache of the matched trie nodes, to skip the walk on repeated publishes. Keyed on the trie's `Arc`, it would need raw pointers into the trie (`unsafe`); holding `Arc`s of trie nodes in the channel or its `Seg` makes a cycle through buffers and events (a message holding its own channel leaks).

## Conventions

- Compile-time guarantees are part of the API. When changing navigation or publishing, update the `compile_fail` doctests in `lib.rs` and the "Compile-time checks" section of the README.
- Every handle and future must stay `Send + Sync`, and messages are `Send + Sync + 'static`.
- Generated code follows Rust naming conventions: names are snake case (modules, methods, subject segments) and become camel case `Topic` variants and leaf types (`PushLeaf`). Only clippy lints about method names (`clippy::new_ret_no_self`, …) are silenced, since `Steps` methods are topic names.
- Logging goes through the `trace!`/`debug!`/`warning!` macros in `src/log.rs`, which compile to nothing without the `tracing` feature. Records keep the default target (their module, `nattes::bus`); levels: `trace` per publish, `debug` for routine events and errors also returned to the caller, `warn` only for what the user must fix, never `info`/`error`. Long-lived operations (`Bridge::run`) run in a span with `instrument!`; no spans on hot paths. Never log while holding a lock: a tracing subscriber is user code. Format subjects and patterns lazily (`subject = %Subject(..)`, `pattern = %Pattern(..)`), never with `subject()`. The test is its own binary (`tests/tracing.rs`) because tracing caches callsite interest globally, so it races with tests on other threads.
- Never drop a user value (an event, a filter, the old trie holding them) while holding a lock: its `Drop` is user code and may publish or unsubscribe. Move it out and drop it after unlocking (`Buffer::try_push`/`close`, `Bus::unsubscribe`). The `*_on_drop`/`dropped_filter_*` tests run on a thread with a timeout, so a regression fails instead of hanging.
- Use the terms of `doc/src/vocabulary.md` in code, docs and comments; don't introduce synonyms. Update it when a concept is added or renamed.
- Scope rule: code goes into nattes only if it can't be done from outside with a common library at no speed cost (it needs the trie, a buffer's lock, delivery counts, or doing it outside adds a buffer, a wake or a task). Everything else (timeouts, non-async receive and publish via `now_or_never`, `Sink` adapters, framing, reconnection, serialization) is a recipe in the README.
